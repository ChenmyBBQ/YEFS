# 空域修改计划表

## 1. 当前问题

当前空域模块的核心问题是没有统一的空域数据模型。

具体表现为：

- UI、控制层、引擎层、持久化层使用的数据结构不一致。
- `QVariantMap`、`QVariantList`、`GeoJSON` 同时承担业务模型职责。
- 绘制态、预览态、正式显示态、持久化态耦合在一起。
- 数据语义依赖 key、数组位置和临时约定，理解和维护成本高。
- `GeoJSON` 过早进入编辑和预览流程，不适合作为核心工作模型。

## 2. 解决方案

建立统一的空域领域模型，并以它作为全链路唯一核心数据结构。

方案如下：

- 定义统一空域对象，包含类型、空间信息、图形特征、数据特征、显示特征。
- 定义编辑态草稿对象，专门承载绘制中的控制点、临时参数和编辑状态。
- 定义统一几何结构，供 UI、控制层、引擎层共同使用。
- `GeoJSON` 只在持久化和正式渲染时使用。
- 提供双向转换工具：自定义空域对象与 `GeoJSON` 互转。
- `QVariantMap`、`QVariantList` 只保留在 QML 和消息总线边界，不再作为核心业务模型。

## 3. 达到的目的

改造完成后应达到以下目的：

- 系统中只有一套统一的空域核心表达。
- UI 到控制层、控制层到引擎、持久化到恢复加载，都围绕同一个空域对象工作。
- 绘制和预览流程不再依赖 `GeoJSON`。
- 持久化和正式渲染边界清晰，`GeoJSON` 只作为边界格式使用。
- 新增空域类型、属性和规则时，不需要在全链路继续堆临时结构。
- 代码更容易理解、维护和测试。

## 4. 需要考虑的细节

### 4.1 空域基础字段

需要考虑：空域 id、类型、经纬度、高度。

解决方案：定义统一基础对象，保证所有层使用同一套字段。

### 4.2 图形特征

需要考虑：半径、宽度、角度、控制点、旋转角等如何表达。

解决方案：按图形类型定义明确的几何结构，不再依赖临时字段推断。

### 4.3 数据特征

需要考虑：状态、数据含义、备注、来源、扩展属性如何管理。

解决方案：建立统一元数据结构，集中管理业务属性。

### 4.4 显示特征

需要考虑：颜色、线宽、透明度、虚线等样式如何统一。

解决方案：建立统一样式结构，UI、引擎、持久化都基于它工作。

### 4.5 编辑态与正式态

需要考虑：绘制中的对象和已保存对象语义不同。

解决方案：正式空域与编辑草稿分开建模，控制器只操作草稿对象。

### 4.6 预览与正式渲染

需要考虑：预览是否继续使用 `GeoJSON`。

解决方案：预览使用自定义几何结构或点集，正式渲染时再转换为目标格式。

### 4.7 持久化边界

需要考虑：什么时候转 `GeoJSON`，旧数据如何兼容。

解决方案：只在保存和恢复时做 `GeoJSON` 转换，并提供双向转换工具。

### 4.8 UI 和消息总线边界

需要考虑：QML 和 MessageBus 是否继续直接承载业务对象。

解决方案：边界层只传轻量参数或桥接数据，核心模型不再散落为松散结构。

### 4.9 合法性校验

需要考虑：不同空域类型参数是否合法。

解决方案：建立统一校验器，在保存和关键状态切换前检查。

### 4.10 兼容与迁移

需要考虑：旧逻辑和旧数据依赖当前结构。

解决方案：先引入新模型，再逐步替换旧链路，保留兼容转换层。
